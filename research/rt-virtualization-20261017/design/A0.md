# A0：有界IRQ服务等级继承实验

FIFO80目标vCPU通过默认Fair的deferred signal worker被唤醒时，中间服务阶段可能受较低等级FIFO任务阻挡。该实验在AArch64 axtest内提供off/inherit/bounded三态：off保留默认Fair；inherit仅对FIFO目标继承其等级；bounded再限制每run的worker派发轮数。生产构建未启用该机制。

VIRQ_IRQ_SERVICE_ROUNDS范围1..256、VIRQ_IRQ_SERVICE_WINDOW_US范围100..100000，默认8轮/1ms。限额状态只归固定worker所有；等待期间保留canonical pending和sticky通知，醒来先检查停止。原有IRQ发布、IPI、队列、设备确认及stop/join所有权不变。限额是派发轮数，不是CPU执行预算、IRQ速率保证或任意滑动窗口上界；实际停止时间还受宿主调度影响。

```sh
# 在analysis/README.md的原生PPI命令前设置以下变量。
export VIRQ_IRQ_SERVICE=inherit VIRQ_INVERSION_WITNESS=1

# 以50ms窗口触发限额；与默认1ms配置分开分析。
export VIRQ_IRQ_SERVICE=bounded VIRQ_INVERSION_WITNESS=0 VIRQ_IRQ_SERVICE_ROUNDS=8 \
VIRQ_IRQ_SERVICE_WINDOW_US=50000

python3 virtualization/axvm/tests/analysis/analyze_virq_irq_service.py \
  run.log --output-dir results

# 只有实际触发限额且独立时间下界成立，才接受该路径的证明。
python3 virtualization/axvm/tests/analysis/analyze_virq_irq_service.py \
  throttle.log --require-throttle --output-dir throttle-results
```

有限FIFO60阻挡任务固定在服务CPU0，仅在第一条延迟PPI arm后激活，并在所有退出路径join。实际IRQ必须在阻挡期间到达；独立校准Guest时间戳判断ISR在阻挡结束前还是之后。off两种目标均在阻挡后执行ISR；inherit/bounded仅FIFO80目标在阻挡结束前执行。临时去掉继承后，相同启用模式的测例失败，四个worker及VM均回收。这是所构造场景中的调度顺序证据，不能将50ms人为阻挡造成的差别解释为真实负载的尾延迟收益。

9组正向共1472条响应和1152条校准，另做原实现敏感度与缺失等待故障验证。正常1ms配置未触发等待；两个8轮/50ms压力组各实际等待7次、所有IRQ完成，独立Guest时间跨度均超过300ms保守下界。省略实际sleep但保留限流计数后，原生IRQ功能测试仍通过，独立时间下界会拒绝；恢复后两层检查通过。因此不能仅凭waits计数声称限额有效。

三态各自的Host ELF/bin、Guest ELF/bin完全相同，实际完整Host CPIO的文件内容仅irq_service字段不同；原始三态与新增witness三态分别核对，不跨不同测试夹具混合性能分布。21项定向静态检查通过。Linux并行组也通过，但普通Guest在独立CPU3，尚未证明同核公平性保护、内存干扰隔离或真实吞吐代价。

A0是已有等级继承与限流思想的控制原型，不声称Deadline感知、论文创新、实板性能或硬实时保证。后续应以匹配负载下的收益、普通VM代价与先行工作对照决定是否扩展A1。高风险调度设计及实现须经过领域审查后才能合入。
